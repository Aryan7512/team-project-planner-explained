A walk through the code

What happens inside the team project planner

The planner is a small Django service that keeps users, teams and project boards, and answers every request with JSON. This page follows real requests through the real code. Every request, response, error message, line of code and SQL statement shown here was recorded by running the planner itself; none of it was typed by hand.

01

The brief

The assignment arrived as three Python classes with empty methods. Each method had a docstring describing the JSON it receives, the JSON it returns and the rules it must enforce, such as user name must be unique or you can only close boards with all tasks marked as COMPLETE.

The task was to write a module that extends those classes, built with Django, which keeps its data in local files inside a db folder and can export a board as a text file into an out folder. Requests and responses are JSON strings, and a method must raise an exception when its input breaks a rule.

02

One request, start to finish

The ten methods that change stored data handle a request in the same five steps. A request that breaks a rule stops at the step that catches it, and nothing after that step runs. The seven methods that only read parse and check their request the same way (two of them, list_users and list_teams, take none), then look up what was asked for and reply without opening a transaction. export_board reads a board and writes a file to out instead of saving to the database.

  1. Parse. The text must be valid JSON, and it must describe an object.
  2. Check. Required fields must be present, and every field sent must have the right type and fit its length limit. Surrounding whitespace is trimmed first.
  3. Rules. A database transaction starts and takes the write lock. The planner looks up every id in the request and applies the rules that depend on stored data: names that must be unique, the fifty-member cap, boards that must be open.
  4. Save. The changes are written and the transaction commits.
  5. Reply. The method returns a JSON string.

Steps three and four share one transaction, so a request that fails at step three ends in a rollback and leaves the database exactly as it was.

A request rejected at step three has already talked to the database. A taken name, an unknown id or a closed board can only be discovered by reading stored data, so the planner asks, finds the problem and ends the transaction with ROLLBACK; the row counts before and after are identical. Requests rejected at steps one and two never open a transaction at all.

03

Where the data lives

Everything the planner stores lives in one file, db/planner.sqlite3. Django turns five model classes into five SQLite tables, and the planner reads and writes them only through Django, so callers only ever see the APIs.

Every row has a random UUID as its id and records when it was created. Users and teams are linked through a separate membership table, which is how one user can belong to many teams. A team's admin is only a reference to a user: being admin does not create a membership.

The rules that matter most are written into the tables themselves as well as into the Python code: unique names, one membership per user per team, only known statuses, and a closed board always having an end time. If a bug ever skipped a check in the code, the database would still refuse the row.

04

A team has fifty seats

The brief says to cap the max users that can be added to 50. The planner reads that as a limit on the team: at most fifty members, and so at most fifty ids in any one add or remove request. A limit on each request alone would let a team grow past fifty, one request at a time.

Three more rules shape every change. Users who are already members are skipped, not counted twice. One unknown id fails the whole request, so nobody in that batch is added. And the admin sits outside the fifty, because being admin is not membership.

05

A board, from open to closed

A board holds a team's tasks. While the board is open, a task can move between OPEN, IN_PROGRESS and COMPLETE in any direction. The brief allows a board to close only when every one of its tasks is COMPLETE. Closing records an end time and takes the board off the team's list of open boards.

After that the board is frozen: no new tasks, no status changes, and it cannot be closed a second time. Reopening a task would break the rule the board was closed under.

06

Two requests at the same moment

Adding users to a team is a check followed by a write: count the members, then add the new ones. If two requests could both count before either wrote, both would see room, and together they could overfill the team.

SQLite lets only one connection write at a time. One line in the planner's settings makes each write transaction take that lock as soon as it begins, before it counts anything. A second request then waits until the first has committed, then counts, and gets the planner's own error.

To test it, separate processes each tried to add a batch of different users to the same empty team at the same moment. Only one batch can fit. The experiment ran with the setting and, for comparison, with that one line removed.

Without the setting the cap still held, because SQLite refused the conflicting writes. But a losing request could get back either the planner's InvalidStateError or a raw OperationalError saying database is locked, depending on timing. With the setting, every losing request waits its turn and gets InvalidStateError.

07

The board export

export_board writes a board to a text file in out and returns the file's name. The file is meant for a person, so it reads top to bottom like the board itself.

It is plain UTF-8, 72 characters wide, with no right-hand borders, so names in any language or with emoji cannot break the layout. Line breaks and control characters inside names and descriptions become spaces. Every export gets a new file: an export in the same second as an earlier one gets -2 on its name instead of replacing it.

09

How we know it works

The behaviour shown on this page is covered by the planner's own tests, apart from the race in chapter 6, which depends too much on timing for a test and was run as the experiment shown there. The tests try every limit from both sides, every error path, data surviving between separate processes, the exact export layout and the HTTP endpoints. GitHub runs the whole suite on every push.

The planted-bug check earned its place during development. Its first round found a gap: the tests did not notice when the progress percentage was rounded up instead of down, because the sample board gave the same number either way. A test for a case where the two differ was added, and that bug is now caught, as the table shows.

10

The same methods over HTTP

The same eighteen methods are also available over HTTP through a thin Django view, at /api/<group>/<method>. Methods that take a request are called with POST and a JSON body, which is handed to the method unchanged. list_users and list_teams take no request and use GET. The response body is exactly what the method returns, and planner errors become JSON with a matching status code.

Requests must be sent as application/json. Browsers will not send that to another site without its permission, which this server never gives, so a web page cannot quietly send requests to a planner running on your machine. The API sets no cookies and has no logins, so there is nothing for Django's CSRF protection to guard.
